**D-021 Architecture on Cloudflare.** Working default. Details to go in `architecture.md`.
- One Worker per school serves the static web app (Workers Static Assets) and the API under `/api/`, on one origin: no CORS, no cross-site cookies, no separate domain needed while testing.
- API in Hono with `@hono/zod-openapi`; Zod for all input and output; the OpenAPI contract is committed and the web client is generated from it. Web is Next.js static export.
- D1 with hand-written SQL migrations, **no ORM**. One database round trip per request; atomic changes in one `batch()`; ledger and audit protected by triggers and a hash chain with a daily export.
- Sessions: `__Host-` cookies, a 10-minute signed access token, a rotating refresh session in the database. Money, approval and publish actions re-check assignments inside their own batch. Non-GET requests must be same-origin.
- Passwords with scrypt (N=2^15). Jobs on Cloudflare Queues and Cron Triggers. PDFs on Browser Rendering, generated in batches.
- Tests with Vitest on the Workers runtime, plus property-based tests for ledger invariants.

**D-023 Base schema and keyed audit chain.** Working default. Migration `apps/api/migrations/0001_foundation.sql`.
Tables are plural (`users`, `role_assignments`, `audit_events`). The database refuses impossible role and scope pairs (an Admin limited to a section, a Student with institution scope), duplicate assignments, and case-different duplicate emails. The audit log is an **HMAC chain** keyed by the `AUDIT_HMAC_KEY` Worker secret, which is never stored in the database, so someone with database access alone cannot rewrite history and still verify. Triggers block edits and deletes and refuse an entry that does not link to the current head; a losing writer's whole batch, business change included, rolls back and retries. Detects an edited entry, a middle insert or delete, and a tampered head. **Known limit:** deleting the newest entries together with the head is invisible inside the database and is caught only by the daily export of `auditChainSummary` (to build in Phase 10). Tested on the simulated database and on a real, temporary D1 database.

**D-024 Sign-in and sessions.** Working default. Amends D-021 (access token 10 to 30 minutes). Migration `0002_sessions.sql`.
- Passwords: scrypt (N=2^15) with `@noble/hashes`, NFKC-normalised, stored as `scrypt$N$r$p$salt$hash`; a hash with weaker settings is upgraded at the next sign-in; stored cost parameters are capped so a tampered row cannot burn CPU. Policy: 10 to 128 characters (counted as characters, so Nepali passphrases are not penalised), not a common password, not containing the email name. **OPEN:** a fuller breached-password check.
- Access token 30 minutes, because every renewal is a D1 write (free plan: 100,000 a day). Roles are in the token; money, approval and publish actions re-check assignments in their own batch.
- Refresh token: random, stored only as a SHA-256 hash, rotated on every use with a conditional update (two simultaneous refreshes: one wins). Reuse of the previous token within 20 seconds is treated as two tabs racing (retry); later, as theft, and the session is revoked. Sessions end after 30 days, or 7 days unused. A deactivated user's session ends at the next refresh.
- Lockout: 5 failures per email and 30 per address in 15 minutes. Unknown emails are locked identically, and wrong-password and unknown-email answers are identical, so nothing reveals which emails exist. Throttled attempts write nothing.
- Sign-in attempts are stored in an append-only `sign_in_events` table (the Admin Sign-ins view, later). `POST /api/auth/sign-in`, `/refresh` and `/sign-out` are public; `GET /api/auth/me` is "any signed-in user". Both lists are reviewed allowlists.
- **Known limit, tested and documented:** after sign-out the access cookie works until it expires (at most 30 minutes).

**D-025 Permission layer.** Working default. Code in `apps/api/src/core/permissions`.
The matrix lives in code (61 actions, 8 groups, from the reviewed `permission-matrix.md` draft), and the document's tables are generated from it, with a CI check so they cannot drift. A route declares an action; no sign-in is 401, no granting role is 403, and the handler never runs. The handler gets a **grant** (institution, sections, own, assigned, class, limits, read-only) and builds its queries from it. Section-scoped Co-ordinators and Accountants narrow to their section by data, with no code change (D-004). Unknown actions, unknown roles and roles not listed are denied. Combined roles union, widest wins. Tested three ways: one generated test per row, hand-written independent rules for the sensitive actions (these caught corrupted cells that generated tests could not), and every role against every action over HTTP. Mutation-tested (9 breakages caught). **Still to do:** money, approval and publish actions re-check assignments inside their own batch (with each module in Phases 3, 6 and 7), and data-level tests per module.

**D-026 School configuration, themes and packs.** Working default. Migration `0003_configuration.sql`, code in `apps/api/src/core/{config,theme}` and `modules/config`, packs in `packs/<school>/pack.json`.
- A **pack** is one school as data: name, sections, optional-module switches, renamed words, theme. `parsePack` checks it and lists every problem at once. Unknown fields, unknown modules, unknown terms, and a theme that fails the readability check are refused.
- Ten modules are **mandatory** (accounts, admissions, academics, approvals, audit, content, fees, files, notifications, results) because they carry rules that must always hold; a pack cannot switch them off. Five are optional (attendance, teacher attendance, homework, notes, top 20) and default on. Renaming is limited to a catalogue of known words (roles and a few terms); nothing else can be renamed.
- Applying a pack **only adds and updates, never deletes**, and is safe to repeat (tested: the second and third run change nothing). A section removed from a pack stays in the database. It runs as one batch. `applyPack` is used by tests; `npm run provision -- --pack <dir> --local|--remote [--config …]` renders the same operations to SQL (values escaped, line breaks and NUL refused) and runs migrations and then the SQL through wrangler. Provisioning is not a user action and is **not in the audit chain**; the pack in git is its record. Provisioning outside the audit log is deliberate and stated here so nobody is surprised.
- Configuration is **public read**: `GET /api/config/public` (name, sections, modules, words, theme; no secrets; cached 60 s; 503 until a pack is applied), one database round trip. Changing the theme is `PUT /api/config/theme`, action `branding.manage` (Super Admin only), written with an audit entry that names the actor, in one batch with the change. The old theme is kept; the database allows only one active theme.
- **Theme readability is enforced on the server**, not only in a screen: WCAG 2.2 contrast, 4.5 for text pairs, 3 for the primary colour against the page, checked for light and dark. An unreadable theme is refused with 422 and the list of failing pairs, and nothing is saved. Fonts come from a fixed list (system, Inter, Noto Sans); no URLs.
- `scripts/check-boundaries.mjs` runs in CI: core never imports modules; a module never reaches into another module's internals; no source imports `packs/`; no source file names a specific school. It already caught a school name in the password denylist, now removed.

Found on staging: an anonymous call with a bad body got 400 (and so learned what the route expects) instead of 401. Now anonymous gets 401 and a role without the action gets 403 whatever they send. **D-028 Design system and app shell.** Working default. Code in `apps/web/src/{ui,shell,theme,config,session,i18n}`.
- **Tokens.** Colours, font and corner radii come only from the school's theme, written into one `<style id="school-theme">` by `theme/css.ts`, which accepts nothing but hex colours, a font from the fixed list and small whole-number radii (so a theme can never inject CSS). Spacing, type scale, elevation and motion are the same for every school (`tokens.css`, no colours in it; shadows are mixed from theme colours). Input borders use the muted text colour, because the server's contrast rules guarantee it is readable while the decorative border colour is not.
- **No flash.** The built-in neutral theme is in every page at build time. A returning visitor gets the school's cached theme applied by a tiny inline script before first paint (Next's documented pattern); the very first visit shows the neutral theme for a moment. **OPEN:** to remove that first-visit flash, the Worker could inject the theme into the HTML as it serves it.
- **Configuration at run time.** `ConfigProvider` reads `/api/config/public` (with a localStorage copy for instant paint and offline use). The page title is the school's name, rendered by React as the only `<title>` (Next's metadata title is left out, because Next rewrites it on every client-side navigation).
- **Shell.** One portal layout for every school (header, menu, page; menu is a scrolling row on a phone and a column from 56 rem). The menu is a registry (`shell/nav.ts`) filtered by role and module switch, which is where modules add their entries later (D-008 slot). Real permissions stay on the API (D-025). Roles show the school's own word (`term`), and Super Admin shows as "Support".
- **Session in the browser.** `createRefreshingFetch`: on 401 it renews the session once and repeats the request; any number of simultaneous failures share one refresh (a refresh token works once); `refresh_in_progress` is retried once; sign-in, refresh and sign-out are never refreshed; going offline is not "signed out". Signed-out visitors and expired sessions on the portal are sent to `/sign-in`.
- **Rules checked by tests (fail the build).** No hex, colour function or colour name outside the theme files; no `font-family` outside the theme; transitions and keyframes only on transform and opacity; reduced motion respected; no sentence or label written in a component (all words come from `i18n/messages.ts`; a Nepali catalog is added later with the same keys). The component gallery `/design` is exempt from the words rule and is public (it holds no data).
- **Tested.** Rendered markup for both packs: identical structure, different words; landmarks, skip link, labels wired to fields, errors announced. 58 web tests, 17 deliberate breakages caught. Checked in a real browser (phone and 1280 px, dark mode, wrong and right password, sign-out, live swap from the Royal Softech pack to the sample school), and the deployed staging pages.
- **Not done, on purpose.** Self-hosted font files (Inter, Noto Sans, Noto Sans Devanagari): downloads need PM approval, so the theme names the font and the stack falls back to the device's fonts, which include Devanagari. Nepali toggle, dark/light switch (follows the device), sign-in Enter-key check by a trusted key event (the browser tool cannot send one; the form is a standard `<form>` with a submit button).
- **Known cost.** Every page load by a visitor who is not signed in makes two quiet 401 calls (`/api/auth/me`, then `refresh`), which show as red lines in the browser console. Fine at this scale (free plan: 100,000 requests a day). **OPEN:** avoid it with a non-secret "signed-in" marker cookie.

**D-034 Notifications and jobs.** Working default. Migration `0004_notifications.sql`; code in `apps/api/src/core/{jobs,notifications,email,crypto-box.ts,background.ts}`.
- **Outbox and runner.** A change that needs a notification writes an outbox row in the same batch (`enqueue`), so the message exists if and only if the change does. `drainOutbox` claims an event with a conditional update (a two-minute lease), so two runners never send one message; a failure is retried after 1, 5, 30, 120 and 720 minutes; after 6 attempts the event is given up on (`dead_at`) and its payload wiped. A unique `dedupe_key` means the same event can never be queued twice, and is also the provider's idempotency key. Handlers must be idempotent, because a crashed runner's event is picked up again.
- **No Cloudflare Queues yet (amends the jobs line in `CLAUDE.md` section 4).** A request delivers what it queued straight away (`waitUntil`), and a cron sweep every 5 minutes (`scheduled` in `src/index.ts`) retries whatever failed. One less account resource, still free. Add Queues only if volume needs it.
- **Secrets in the queue are sealed.** `crypto-box` (AES-256-GCM through Web Crypto, key from the `DATA_KEY` Worker secret) encrypts a payload before it is stored; the purpose is bound in, so a sealed value cannot be moved elsewhere and opened. A copy of the database (or its daily export) cannot be used to take over an account.
- **Email is an adapter (D-008 extension point).** Only the `dev` adapter exists: it writes to `dev_mailbox` so development and staging can read what would have been sent. It is refused in production (`validateEnvironment`), like demo mode. A real provider is a Phase 9 adapter. Links in emails use the per-deployment `SITE_ORIGIN`, never the request's Host header, so a forged Host cannot poison a reset link.
- **Tested.** 13 deliberate breakages caught (no lease, no backoff, never gives up, payload kept, stored unsealed, condition ignored, purpose not bound, dev adapter in production, and more). `OPEN:` move the email wording into the message catalog when Nepali is added; rotate `DATA_KEY` (sealed values become unreadable, so it needs a re-seal procedure); clean out old dev mailbox rows.

**D-035 Password reset.** Working default. Migration `0005_password_reset.sql`; `modules/auth/password-reset.ts`; web `/reset-password`.
- **Request** (`POST /api/auth/password-reset/request`, public): always 202, whether or not the address has an account. It is one batch of conditional statements, so the work is the same either way. Limited to 3 an hour per account and 10 an hour per address, so the form cannot flood an inbox. A newer link replaces any older one. **OPEN:** the timing is designed to match but has not been measured.
- **Token:** 256 random bits; only its SHA-256 hash is stored; valid for 1 hour; works once. The link carries it after the `#` (`/reset-password#token=...`), which a browser never sends to a server, so it cannot reach a request log or Referer. The page removes it from the address bar once used.
- **Confirm** (`POST .../confirm`): the password is judged first (so a weak choice leaves the link usable), then the link is claimed with a conditional update (two people using it at once: one wins), then the password is set, every session of the account is ended, other open links are closed, and an audit entry names the person. If the server stops between claiming and setting, the person just asks again: the safe way to fail. Expired, used, unknown and deactivated all answer the same 400.
- **Password rules** now also refuse the school's own name (`schoolNameWords`, from configuration, so no school is named in code; generic words like "college" are ignored) and ignore punctuation inside it, so "r.o.y.a.l" is caught. The same rule applies in `createUser`.
- **Tested:** 26 tests; 12 breakages, 11 caught at first and the survivor (a redundant expiry check) fixed by a new test. Checked live in a browser on localhost and on staging.

**D-036 Two-step sign-in with an authenticator app.** Working default. Migration `0006_two_factor.sql`; `modules/auth/two-factor.ts`, `core/two-factor/`; web `src/two-factor/`.
- **Who:** the Super Admin must (`core/two-factor/policy.ts`, per CLAUDE.md section 7); the Admin too, from D-038. Anyone who has turned it on is asked for the code. Other staff get a code by SMS or email in Phase 9, when those channels exist. ~~**OPEN (PM):** should Admin be required too?~~ Answered yes, D-038.
- **Flow.** After a right password, sign-in returns a *challenge* (signed with the session secret, 5 minutes, not a session) instead of cookies: `required` (enter the code) or `setup` (set the app up first). `POST /api/auth/2fa/verify` exchanges it for a session; `/setup` returns a new secret and an `otpauth://` address; `/enable` confirms the first code, turns it on, signs in and returns ten recovery codes, shown once. A session is never issued before the second step is done.
- **Codes:** RFC 6238 through the `otpauth` library (SHA-1, 6 digits, 30 s, one step either side), checked against the RFC's own test vectors. A code works once: the newest accepted time step is claimed with a conditional update (a replay, or two simultaneous submissions, cannot both win). Wrong codes count toward the same lockout as wrong passwords (5 an email in 15 minutes) and a throttled attempt writes nothing.
- **Secret:** stored sealed, bound to the person (D-034), so a copy of the table cannot make codes and a sealed secret copied to another row will not open. Setup never overwrites a confirmed secret.
- **Recovery:** ten single-use codes stored as hashes; using one is audited. **Reset for a lost phone:** `POST /api/users/{id}/two-factor/reset` (action `accounts.reset_2fa`, Super Admin only) removes it, ends the person's sessions and audits who did it. Nobody resets their own, since a stolen session could otherwise switch the protection off. **OPEN:** with only one Super Admin who loses both phone and codes, nobody can reset it; recovery is an operator procedure (Phase 10). **OPEN:** regenerate recovery codes; a QR code for setup (the key is shown to type or copy, and an "open in authenticator app" link works on a phone).
- **Screens (Apple review, D-029):** one prominent button per step; the code field offers the number keypad and one-time-code autofill (`entering-data.md`, `text-fields.md`); a wrong code keeps the cursor in the field with a message that says what to do (`writing.md › error messages`); the method is named "authenticator app" (`managing-accounts.md`); recovery codes need an explicit "I have saved these codes" before entering (the session is held back until then); "Copied" is announced to screen readers (`feedback.md`). **Judgment:** the setup key in groups of four. **Limits:** not reviewed on a real phone or with a screen reader; `ui-ux-pro-max` (D-032) was not used for these screens because it was not loaded in the session that built them.
- **Tested:** 53 API tests and 15 web tests. 19 breakages: 15 caught first time, 2 redundant-layer survivors (the read-side replay check and the conditional-update guard each have a second layer that still holds in sequential tests), 2 re-run and caught.
