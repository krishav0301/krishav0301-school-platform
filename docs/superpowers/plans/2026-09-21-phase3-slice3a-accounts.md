# Phase 3, Slice 3a: Staff Accounts and the First Password Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The Admin creates Co-ordinators and Accountants, the Co-ordinator creates teachers, each new person gets a one-time temporary password and must choose their own before any session; whoever may deactivate a person may also reactivate them and issue a new temporary password.

**Architecture:** Extends the `accounts` module (staff services and routes) and the `auth` module (a `password` challenge kind, a forced-change step in sign-in, and one new endpoint). Same write pattern as slices 1 and 2: one audited `recordAudit` batch with the actor re-checked in SQL. New People screen and a "Choose a new password" step on the sign-in screen.

**Tech Stack:** Cloudflare Workers, Hono with `@hono/zod-openapi`, D1, `@noble/hashes` scrypt through `core/passwords`, Web Crypto, Next.js static export.

**Spec:** `docs/superpowers/specs/2026-09-21-phase3-academic-setup-design.md`, section 6.1 (approved by the PM in chat, 2026-09-21). Decision to log: D-059.

**Format:** as in slice 2's plan: tasks, files, interfaces and exact test cases; the code is written straight into the files, tests first.

## Global Constraints

- Everything in slices 1 and 2's Global Constraints still holds (one audited batch per write with `onlyIfLastChanged`, actor re-checked in SQL, `public_id` only to clients, no hard deletes, words in `messages.ts`, tokens only, 44 px controls, modules call each other's `index`/`service` only, every commit ends with `Co-Authored-By: Claude Sonnet 5 <noreply@anthropic.com>`).
- **The temporary password is a secret:** returned once with `Cache-Control: no-store`; never stored in the clear; never in an audit entry, an outbox payload, a log line or a test snapshot. Only its hash is stored.
- **Nobody changes their own account** through the staff routes (deactivate, reactivate, new temporary password).
- **A challenge is single-purpose:** a `password` challenge opens only the change-required endpoint; a `verify` or `setup` challenge never opens it.
- Branch `phase3-slice3a-accounts`. Slice 3b (teaching) is a separate branch and PR.

## Tasks

### Task 1: `staff_profiles` (`apps/api/migrations/0011_staff.sql`)
`staff_profiles(user_id INTEGER PRIMARY KEY REFERENCES users(id), home_section_id INTEGER REFERENCES sections(id))`. Test first (`staff-schema.test.ts`): one row per user; a section that does not exist is refused; a null home section is allowed.

### Task 2: Two permission rows
`accounts.staff.view` (Admin `read`, Co-ordinator `inst` with limit "teachers", Super Admin `all`; phase 3) and `accounts.password.issue` (same cells and limits as `accounts.deactivate`; phase 3), in `matrix.ts` next to their neighbours. Test first in `permission-matrix.test.ts`: `exactly` entries for both; the limits read "teachers" and "co-ordinators, accountants"; nobody but those roles may issue a password. Regenerate `docs/permission-matrix.md`.

### Task 3: The temporary password generator
`apps/api/src/core/temporary-password.ts`: `generateTemporaryPassword(): string` (16 characters of `ABCDEFGHJKMNPQRSTUVWXYZ23456789`, grouped `XXXX-XXXX-XXXX-XXXX`, Web Crypto with rejection sampling so no character is likelier). Test first: format and length; only the alphabet; 1000 draws are all different; the spread of characters is even (no character more than about 2 times its share); every result passes `passwordProblems` for a normal email and school name.

### Task 4: The forced change at sign-in (auth)
Files: `core/two-factor/challenge.ts` (kind `password`; `verifyChallenge` accepts it), `modules/auth/service.ts` (`signIn` reads `must_change_password` and, when the password is right and the flag is set, records `password_ok_must_change` and returns `{ ok: true, passwordChange: "required", challenge }` before any second step), new `modules/auth/first-password.ts` (`changeRequiredPassword(deps, input { challenge, password, ip, userAgent }, now)`), `modules/auth/routes.ts` (the sign-in response union gains the step; new route `POST /api/auth/password/change-required`, public, body `{ challenge, password }`; 200 session or `TwoFactorStep`; 401 `invalid_challenge`; 422 `weak_password` with problems, or `same_password`), the two-factor services must refuse a `password` challenge. Test first (`auth.test.ts` additions or `password-change.test.ts`):
- sign-in of a flagged person returns the step and **no cookies and no session**; a person without the flag signs in as before; a wrong password still returns 401 with the same answer; the sign-in event is recorded.
- the change endpoint: a valid challenge and a good password clears the flag, stores a new hash (the old password stops working, the new one works), records `accounts.password.changed` with the person as actor (and **no** password in the entry), and returns a session for a person with no second step; for an Admin or Super Admin it returns the authenticator step instead of a session.
- refused: a weak password (each policy reason, including the school's name and the email) leaves the flag set and the challenge usable; the temporary password itself is `same_password`; a forged, expired, or `verify`/`setup` challenge is 401; the same challenge used twice (flag already cleared) is 401; a deactivated person is 401.
- a `password` challenge sent to the verify, setup and enable endpoints is refused.

### Task 5: The staff services (accounts)
Files: `modules/accounts/staff.ts` (new), `modules/accounts/service.ts` (re-export), guard SQL in `modules/accounts/guard.ts` (new: `mayManagePerson(n, targetExpr)` written as one SQL fragment: an active Super Admin; or an active Admin and the target has an active Co-ordinator or Accountant role; or an active Co-ordinator and the target has an active teacher role and (the Co-ordinator is institution-wide or the target's home section is the Co-ordinator's section); and the target is never the actor), `staff.ts` functions: `createStaff(db, auditKey, actor, input, now?)` (Co-ordinator or Accountant; institution or section scope), `createTeacher(db, auditKey, actor, input, now?)` (home section), `setStaffActive(db, auditKey, actor, targetId, active, now?)` (deactivating also ends the target's sessions, in the same batch and under the same guard), `issueTemporaryPassword(db, auditKey, actor, targetId, now?)` (new hash, `must_change_password = 1`, ends sessions, clears the lockout), `listStaff(db, viewerRoles)`. Test first (`staff-service.test.ts`, copy `academics-programmes.test.ts`): every create/act success and audit entry, with the temporary password **not** in the audit entry and not in the database; each role that may not (a Co-ordinator creating a Co-ordinator, an Admin creating a teacher, a teacher, an accountant, a student) is `not_allowed` with nothing written; a section-scoped Co-ordinator creates a teacher only in their own section (another section is `not_allowed`) and manages only their own section's teachers; a repeat email in another letter case is `conflict` with no orphan row and no audit entry; nobody acts on themselves; the Admin cannot touch a teacher, the Co-ordinator cannot touch a Co-ordinator or an Accountant; the Super Admin can touch anyone but themselves; a switched-off actor with a valid token is refused; deactivation ends sessions (a session row is revoked) and the person can no longer sign in; reactivation lets them; a new temporary password forces the change again and the old password stops working; `listStaff` shows an Admin all staff, a Co-ordinator only teachers, a section-scoped Co-ordinator only their own section's teachers, and never a Super Admin.

### Task 6: The staff routes and the contract

Create and issue responses carry `temporaryPassword` and `Cache-Control: no-store`. Test first (`staff-routes.test.ts`): 401 signed out; 403 for students, teachers, accountants on everything; the Admin may create Co-ordinators and Accountants (201) but not teachers (403), and may list; a Co-ordinator creates teachers (201) but not a Co-ordinator (403); section-scoped data-level tests (a +2 Co-ordinator cannot see, deactivate or re-password a Bachelor's teacher, even with a guessed id); the whole flow from the outside (create, sign in with the temporary password gives the step, change it, sign in with the new one); `no-store` on the secret responses; the password never appears in the list response. Then `npm run gen:openapi`, `npm run gen:api` in `apps/web`, the full API suite, `check-boundaries`.
