# FUT 2026-10-05 points: implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build FUT points 1, 2, 4, 5, 6, 7, 7b, 8, 9, 11, 13, 14 and 15 as approved in the spec.

**Architecture:** Mostly configuration and screens on top of what D-110 built. Two real rule changes on the server: a term accepts only levels whose length (months) matches the term's, and a subject belongs to one wing. One migration (0031) rebuilds `subjects` with a wing. Everything else is the web app: a shared Wing › Course › Level picker, and screen fixes.

**Tech Stack:** Cloudflare Worker (Hono, zod-openapi), D1 with hand-written SQL, Next.js static export, Vitest.

**Spec:** `docs/superpowers/specs/2026-10-05-fut-15-points-design.md`

**Plan form.** Compact, as on Phase 3 slice 2 (the PM accepted it then): tasks, files, interfaces, the exact test cases and the key code. Tests are written first in each task and seen to fail for the right reason.

## Global Constraints

- One database round trip per request where the code already does so; atomic changes are one `batch()` with conditional SQL; every write emits its audit entry in the same batch (`write()` in `academics/write.ts`).
- No permission rows change (`core/permissions/matrix.ts` untouched). A route's permission is checked before its body.
- BS conversion only through `apps/api/src/core/dates` (and `formatBsDate`/BS parts already in the web). No new conversion tables.
- No hardcoded colours, fonts or words in components; every new word goes in `apps/web/src/i18n/messages.ts` and is used.
- The school's words come from terms: `term.section` (Wing), `term.programme` (Course), `term.level` (Level), new `term.classSection` (Section).
- Migrations are backward compatible with the Worker running before the deploy; packs only add and update.
- Level length: `levels.usual_months`, 1 to 60.
- Term months: `round(((eY*12+eM) - (sY*12+sM)) + (eD - sD + 1) / 30)` on the BS parts of start and end. Same formula on server (authority) and web (filter only).
- Every changed screen: `ui-ux-pro-max` before, `apple-design` review after, 320 px with text at 200%, one prominent button per view, 44 px controls.

**Interfaces:** Produces `termMonths(startAd: string, endAd: string): number` (exported for tests). API: `AcademicYear.months: number`, `TermLevel.usualMonths: number | null`.

- [ ] Failing tests:
  - `termMonths("2025-07-17", "2026-01-13")` (1 Shrawan 2082 to 29 Poush 2082) is 6; a full BS year is 12; one day short of 3 months is 3.
  - Create a 6-month term with a 3-month level: refused, `invalid`, message names the level and both lengths; nothing written (no term row, no audit entry).
  - Create with a level whose length is not set: refused, message "Set the length of {level} first".
  - Create with a matching level: accepted.
  - Update an open term that already holds a mismatched level, adding a matching one: accepted (existing levels are flagged, not blocked).
  - Changing a draft term's dates so an existing level no longer matches: refused.
  - A level in another open term: still refused (existing trigger), unchanged message.
- [ ] Implement:

```ts
/** The term's length in whole months, on the BS calendar (spec, "Term months"). */
export function termMonths(startDate: string, endDate: string): number {
  const s = adToBs(startDate);
  const e = adToBs(endDate);
  return Math.round(e.year * 12 + e.month - (s.year * 12 + s.month) + (e.day - s.day + 1) / 30);
}
```

  `inspect` also returns `levels: { id, name, usual_months }[]` for the ids sent (same batch). In `createYear`, every sent level must have `usual_months === termMonths(...)`. In `updateYear`, check the levels being added (not already in the term), and all levels if the dates change. `addLevels` gains `AND lv.usual_months = ?3` so a mismatched level can never be inserted even in a race.
- [ ] Run the term tests, then the whole API suite. Break on purpose: remove the `usual_months` filter from `addLevels` and the service check in turn; a named test fails each time. Commit: "Terms take only levels of their own length (D-114)".

- [ ] Migration (rebuild, as 0030 did for `academic_years`):

```sql
PRAGMA defer_foreign_keys = true;
CREATE TABLE subjects_copy AS SELECT * FROM subjects;
DROP TABLE subjects;
CREATE TABLE subjects (
  id INTEGER PRIMARY KEY,
  public_id TEXT NOT NULL UNIQUE,
  section_id INTEGER REFERENCES sections (id),   -- the wing; NULL only for an old subject not yet sorted
  name TEXT NOT NULL COLLATE NOCASE CHECK (length(name) BETWEEN 1 AND 120),
  code TEXT CHECK (code IS NULL OR length(code) BETWEEN 1 AND 20),
  is_archived INTEGER NOT NULL DEFAULT 0 CHECK (is_archived IN (0, 1))
);
CREATE UNIQUE INDEX subjects_name_in_wing ON subjects (COALESCE(section_id, 0), name COLLATE NOCASE);
CREATE UNIQUE INDEX subjects_code_in_wing ON subjects (COALESCE(section_id, 0), code COLLATE NOCASE) WHERE code IS NOT NULL;
-- The wing a subject is taught in, from its curriculum; NULL when unused or used in both wings.
INSERT INTO subjects (id, public_id, section_id, name, code, is_archived)
SELECT s.id, s.public_id,
       (SELECT CASE WHEN COUNT(DISTINCT p.section_id) = 1 THEN MIN(p.section_id) END
          FROM subject_offerings o JOIN levels l ON l.id = o.level_id JOIN programmes p ON p.id = l.programme_id
         WHERE o.subject_id = s.id),
       s.name, s.code, s.is_archived
  FROM subjects_copy s;
```

Drop `subjects_copy`. Recreate any index or trigger 0010 to 0030 put on `subjects` (check with `grep -n "ON subjects" migrations/*.sql`).
